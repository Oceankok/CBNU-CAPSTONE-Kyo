# 관리자 수동 이벤트 병합 API (#138)

같은 사건인지 자동으로 확정하기 어려운 이벤트는 별도로 저장합니다. 관리자가 비식별 영상을 확인한 후 명시적으로 병합할 수 있도록 백엔드 API를 제공합니다. 구역·시간·PPE만으로 자동 병합하지 않으며, 카메라 보정·Re-ID·좌표 판정도 포함하지 않습니다.

## 기본 범위

- 대표 이벤트와 병합할 이벤트 모두 `pending`이고 검토 기록이 없어야 합니다. `hold`도 검토가 진행된 상태이므로 제외합니다.
- 보관·삭제 결정, 동의 연결, 과거 검토·보관 이력이 없어야 합니다.
- 같은 PPE 유형이어야 합니다. 다른 위반을 한 사건이라는 이유만으로 합치지 않습니다.
- 클립 요청의 `pending`·`failed`, 미디어 처리·삭제, 대기·실행 중 GPU 작업이 있으면 409로 거절합니다. 복구를 시도하거나 확보 불가를 확정한 뒤 다시 요청합니다.
- 이미 다른 이벤트에 병합된 이벤트와, 다른 원본 이벤트를 포함한 대표 이벤트의 재부모화는 허용하지 않습니다. 대표 이벤트에 새로운 원본 이벤트를 추가하는 것은 허용합니다.
- 검토 완료 이벤트 병합과 병합 취소는 이번 기본 구현에 포함하지 않습니다. 프론트 화면은 변경하지 않았습니다.

## 요청

```http
POST /api/events/{대표_event_id}/merge
Authorization: Bearer <관리자 토큰>
Content-Type: application/json

{
  "source_event_ids": ["EVT_B", "EVT_C"],
  "expected_version": 0,
  "reason": "두 카메라의 비식별 영상을 확인하여 동일 사건으로 판단했습니다."
}
```

`source_event_ids`는 대표 이벤트를 제외한 서로 다른 ID 1~20개입니다. 사유는 공백을 제외한 1~1000자입니다. `expected_version`은 대표 이벤트 조회 응답의 `merge_version`이며, 병합한 원본 이벤트 수를 나타냅니다. 같은 버전으로 동시에 요청하면 하나만 성공하고 다른 요청은 409입니다. 중복 요청을 새 병합으로 처리하지 않습니다.

관리자 인증이 없으면 401, 작업자는 403, 존재하지 않는 이벤트는 404, 검토·보관·처리 상태나 버전 충돌은 409, 중복·자기 자신·잘못된 요청값은 422입니다. `merged_by`는 인증한 관리자에서 결정합니다.

응답에는 대표 `event_id`, `merge_version`, `merged_event_ids`, `merged_into_event_id`, `merge_history`가 포함됩니다. 기존 이벤트 상세 응답의 `event`에도 같은 필드를 추가합니다.

## 기록과 영상

원본 `candidate_event` 행과 카메라·탐지 시각·tracking ID는 유지하고 원본의 상태만 `merged`로 변경합니다. 원본 ID로 상세 조회하면 `merged_into_event_id`로 대표 이벤트를 확인할 수 있습니다. 일반 이벤트 목록에서는 원본을 제외합니다.

원본 미디어와 종료된 클립 요청은 대표 이벤트에 연결하고 역할을 `reference`로 변경합니다. 미디어·요청 ID, 촬영 카메라·시각, 파일 경로, 처리 이력은 유지합니다. 실제 파일 복사·삭제나 재인코딩은 하지 않습니다. `merge_history`에는 원본·대표 ID, 관리자, 시각, 사유, 이동한 미디어·요청 ID 목록을 보존합니다.

병합 후 원본에는 새 검토·미디어·클립 요청·방송 요청을 등록할 수 없습니다. 원본으로 자동 리다이렉트하여 새 자료를 접수하지 않습니다. 처리 node가 `GET /api/processing/events/{원본ID}/clip-requests`를 호출하면 409와 `detail: {"code": "event_merged", "merged_into_event_id": "대표ID"}`를 반환하므로 관리자 로그인 없이 대표 ID를 확인할 수 있습니다. 병합 전 클립 요청이 모두 종료되어야 하는 이유도 이 경합을 피하기 위해서입니다.

대표 이벤트에서 모든 연결 미디어를 함께 검토하고 기존 동의·보관·삭제 정책을 적용합니다. 원본의 보관 상태는 과거 초기 상태로 남지만 관리 대상으로 사용하지 않습니다. 삭제 후에도 최소 이벤트·병합·검토 이력은 유지합니다.

병합은 방송을 새로 생성하지 않습니다. 이미 실행·접수된 방송을 되돌리거나 중복 방송을 사후 제거하지 않습니다. 실시간 방송 억제는 기존 cooldown과 통합 단계의 별도 합의에 따릅니다.

## 통계·DB·프론트 연결

원본 `merged` 이벤트는 후보 통계에서 제외하고 대표만 집계합니다. 이미 생성한 분기 요약의 후보 수는 같은 트랜잭션에서 갱신합니다. 확정·오탐·보류 수는 검토 전 사건만 병합하므로 변하지 않습니다. 교육 자료·추천을 삭제하거나 재생성하지 않습니다. 대표의 촬영 시각·분기는 유지하며 대표를 어느 사건으로 선택할지는 관리자가 결정합니다.

SQLite/PostgreSQL 스키마 v13→v14에서 `event_merge`를 추가합니다. #167 → #168 → #170 → 이 PR 순서로 반영합니다. 실제 배포 DB를 이 PR에서 변경하지 않습니다.

프론트 담당은 별도 PR에서 원본 선택·대표 선택·사유 입력·버전 전달, 409 안내, 병합 이력·대표 이동을 연결해야 합니다. 원본의 `merged` 상세는 검토 화면 대신 대표 이벤트 안내로 처리합니다. 기존 단건 검토 화면을 임의 수정하지 않았습니다.

검토 완료 사건 병합, 병합 취소, 자동 병합·카메라 보정은 후속 논의 항목으로 남깁니다.
