# 동의서 등록·보관 연결 API (#117)

관리자 확인을 받은 동의서 PDF와 이벤트 보관 결정을 연결합니다. 사업장 코드는 기록 분류용입니다. 현재 설치의 관리자는 모든 사업장 기록을 관리하며, 회사별 관리자 계정을 격리하는 기능은 추가하지 않습니다. 프론트 화면은 변경하지 않았습니다.

## 프론트 연결 순서

1. 보관 팝업에서 PDF, 사업장 코드, 적용 대상·범위, 양식 버전, 보관 종료 시각을 받습니다. 관리자가 모델 개선용 이용 동의를 확보했고 해당 이벤트에 적용된다는 사실을 직접 확인합니다.
2. `POST /api/consent-records`로 동의서를 등록합니다. 성공한 경우 발급된 `record_id`를 사용합니다. 업로드 실패 시 보관 요청을 보내지 않습니다.
3. 기존 `PUT /api/events/{event_id}/retention`에 아래처럼 발급 번호를 전달합니다. 검토 완료 여부·버전·파일 존재와 해시·철회 여부 검사를 통과해야 보관과 이벤트 연결이 같은 DB 트랜잭션으로 완료됩니다.
4. 같은 동의서가 적용되는 다른 이벤트는 기존 활성 기록을 선택해 3번을 수행할 수 있습니다. 적용 범위 확인은 매번 관리자가 수행합니다.

```json
{
  "decision": "retain",
  "expected_version": 0,
  "consent_confirmed": true,
  "consent_record_id": "CONSENT_<발급된 32자리 ID>",
  "retain_until": "2026-11-15T00:00:00+09:00"
}
```

`consent_reference`는 서버가 `record_id`로 설정합니다. 확인 관리자와 연결 관리자는 인증 정보에서 결정합니다. 프론트에서 관리자 ID나 저장 경로를 전송하지 않습니다. PDF 등록과 보관 요청은 두 요청이며, 보관이 거절되어도 등록된 문서는 관리자 목록에서 재사용할 수 있습니다.

## 엔드포인트

모든 API는 관리자 Bearer 인증이 필요합니다. 미인증은 401, 작업자는 403입니다.

| API | 설명 |
| --- | --- |
| `POST /api/consent-records` | multipart `file`과 JSON 문자열인 `metadata`로 등록, 201 반환 |
| `GET /api/consent-records?site_code=SITE_A&limit=50&offset=0` | 사업장 필터·페이지 조회, 최대 100건 |
| `GET /api/consent-records/{record_id}` | 해시·크기·페이지 수·확인 관리자·상태·버전 조회 |
| `GET /api/consent-records/{record_id}/file` | 인증·파일 해시 검사 후 PDF 첨부 다운로드, 캐시 금지 |
| `POST /api/consent-records/{record_id}/revoke` | `expected_version`, `reason`으로 철회 |

multipart `metadata` 예시는 다음과 같습니다.

```json
{
  "site_code": "SITE_A",
  "scope_description": "프레스 구역 시연 참여자 및 해당 이벤트의 모델 개선용 이용 동의",
  "form_version": "2026-01",
  "consent_confirmed": true
}
```

사업장 코드는 영문·숫자로 시작하며 영문·숫자·`_`·`-`를 사용합니다. `scope_description`은 1~2000자, `form_version`은 1~80자입니다. 공백만 있는 값은 허용하지 않습니다.

## 파일과 동의 확인

PDF만 받으며 최대 10MiB·100페이지입니다. 암호화·빈 파일·손상된 PDF 구조를 거절합니다. SHA-256을 저장하고 보관 연결과 다운로드 때 대조합니다. 구조 검사는 서명·법적 유효성·당사자 신원·문서 내용의 적절성을 판정하지 않으며, OCR·전자서명 검증이나 악성코드 검사를 대신하지 않습니다.

파일은 비공개 볼륨의 `.private_media/consents/`에 서버가 발급한 이름으로 저장합니다. `/storage`로 제공하지 않고, 응답에 파일 경로를 포함하지 않습니다. 업로드 파일의 이름을 저장 경로로 사용하지 않습니다. 파일 게시 또는 DB 기록 저장에 실패하면 등록을 취소하고 임시 파일을 정리합니다. 프로세스 중단으로 남은 미등록 파일은 maintenance가 관리 대상 이름·경로·시간을 검사해 정리합니다.

## 철회와 삭제

철회하면 기록 상태를 `revoked`로 바꾸고, 현재 이 동의 기록으로 보관 중인 이벤트들을 삭제 대상으로 전환합니다. 원본·처리 결과·진행 중 worker 작업은 기존 삭제·취소·cleanup 확인·maintenance 재시도 경로를 사용합니다. 삭제 실패 시 파일이 이미 삭제됐다고 표시하지 않습니다.

이벤트·검토·최소 감사 이력과 동의서 PDF·동의 기록은 유지합니다. 다른 동의 기록의 이벤트는 삭제하지 않습니다. 철회된 기록으로 다시 보관할 수 없습니다. 같은 철회 요청을 다시 보내도 삭제 이력을 중복 생성하지 않습니다.

기존 UI의 자유 입력 `consent_reference` 방식은 호환성을 위해 유지합니다. 다만 구조화된 동의 기록이 이미 연결된 이벤트를 자유 입력 방식으로 덮어쓸 수 없습니다. 프론트 연동 완료 후 신규 보관에서 파일 기반 기록을 필수화하는 변경은 별도로 전환해야 합니다. 기존 자유 입력 기록에 이 기능의 철회가 소급 적용되는 것은 아닙니다.

## DB·백업·배포

스키마 v10→v11에서 `consent_record`, `event_consent`를 추가합니다. 기존 사용자·이벤트·자유 입력 동의 기록은 유지합니다. SQLite와 PostgreSQL 모두 초기화 함수를 반복 실행해도 기존 기록을 보존합니다.

`backend.backup.media`의 기존 스냅샷에 동의서 PDF를 포함합니다. 공개 처리 영상과 별도 `consents/` 항목으로 저장하며, 체크섬·경로·크기와 복원 DB 일치를 검사합니다. 카메라 원본·로그인 자격 증명은 포함하지 않습니다. 동의서가 있는 DB에서 PDF가 빠진 백업은 복원하지 않습니다. 스냅샷은 기존 만료 정책과 접근 제한을 그대로 적용합니다.

배포 전 기존 DB를 백업하고 기존 API·maintenance·worker 쓰기를 멈춘 다음 새 이미지의 `python -m backend.db.init_db`로 이관해야 합니다. `Release.ps1 -InitializeDatabase`는 첫 배포 전용이므로 기존 배포에 사용하지 않습니다. 이 PR에서는 실제 배포 DB를 이관하지 않았습니다. v11 이관 이후 이전 이미지로 되돌리는 경우 DB 호환성도 함께 확인해야 합니다.

## 검증

격리 DB·임시 PDF·합성 미디어로 관리자 권한, 비공개 다운로드, 사업장 필터, 파일 검사, 파일 게시 실패 롤백, 보관 연결 원자성, 파일 변조·소실, 철회 후 실제 파일 삭제·이력 유지, v10 이관, 백업·복원·경로 탈출 차단, 중단 파일 정리를 검증합니다. 실제 동의서나 외부 API는 사용하지 않습니다.
