# W13: 선택적 구역 구성원 비교 후 교체 API

이 문서는 **백엔드 선행 준비**다. 기존 프론트는 보호되지 않으며 프론트 수정/배포 없이 W13 전체 완료를 의미하지 않는다. 운영 설정이나 모델은 바꾸지 않았다.

## 요청
`PUT /api/zones/{zone_name}/members` (관리자 전용)

```json
{"user_ids":["worker01","worker02"],"expected_user_ids":["worker01"]}
```

- `user_ids`: 저장할 전체 명단.
- `expected_user_ids`: 편집 시작 때 조회한 해당 구역의 **전체 구성원 ID** 명단. 비활성 계정도 포함한다. `/api/users` 응답의 `zone_names`를 기준으로 해당 구역 배정을 모두 모은다. 화면에서 검색/필터한 일부 명단을 사용하지 않는다.
- 배열 순서는 무관하고 ID 앞뒤 공백은 기존 user_ids와 같이 정규화한다. 빈 배열은 빈 명단을 뜻한다. null/중복/빈 ID/100자를 넘는 ID/1000개 초과는 422다.
- 필드 생략은 기존 전체교체 동작을 유지한다. optional은 점진적 FE 연결용이며 구 클라이언트 보호가 아니다.

## 결과와 원자성
서버는 기존 쓰기 잠금을 얻은 뒤 최신 명단과 expected_user_ids를 비교하고 같은 transaction에서 교체한다. 다르면 `409 {"detail":"zone_members_changed"}`이며 DB를 변경하지 않는다. 일치하면 기존 200 응답 `{"zone_name":"A","user_ids":[...]}`을 반환한다.

구역 전체교체뿐 아니라 사용자 생성·사용자 zone_names/scalar 변경 경로의 변경도 현재 명단으로 확인한다. 이들 기존 경로는 동일 쓰기 잠금을 사용한다. 다른 구역 배정과 기존 scalar 투영은 유지된다. 없는 구역 404와 관리자만 사용 가능한 기존 접근제어도 유지된다.

## 프론트가 연결할 동작
1. 최신 구성원 전체를 조회하고 초기 ID 배열을 편집값과 별도로 보존한다.
2. 저장할 때 편집값은 user_ids, 초기 배열은 expected_user_ids로 보낸다.
3. 409이면 자동 덮어쓰기/자동 재시도하지 않는다. 사용자 편집 내용을 보존하고 최신 명단을 다시 읽어 충돌 안내 후 다시 선택하게 한다.
4. 성공하면 응답 user_ids를 새 초기 배열로 교체한다.
5. 네트워크 단절로 성공 여부가 불명확하면 재조회로 확인한다. 같은 요청의 무조건 재전송은 성공 후에도 409일 수 있다.

## 제한
- 전역/구역 revision이나 이력 토큰이 아니라 **현재 명단 일치** 검사다. 중간에 변경됐다가 같은 명단으로 복귀한 경우는 허용한다. 구성원 집합이 같으므로 이 검사는 이력 감지를 보장하지 않는다.
- 기존 필드 없는 전체교체나 사용자 편집 경로를 이용한 이후 변경은 여전히 마지막 쓰기 우선이다. 모든 편집 UI를 연결하고 구 요청 허용 여부를 결정해야 시스템 전체 유실 방지라고 할 수 있다.
- 별도 신규 DB 이관은 없다. 새 명단 조회 endpoint도 만들지 않았다.
- SQLite 실제 병렬 쓰기 테스트를 포함한다. 새 patch의 실제 PostgreSQL 동시성 검증은 별도로 수행해야 한다. 기존108파일 PG419 통과를 이 변경에 자동 적용하지 않는다.
