# 카메라 그룹과 참고 영상 요청의 기본 API (#138)

목표는 한 이벤트에서 같은 장소를 촬영한 다른 카메라의 영상을 확인하는 것입니다. 관리자가 겹치는 촬영 구역의 카메라를 명시적으로 그룹에 등록하면, 새 이벤트 생성 시 같은 그룹의 다른 활성 카메라에 대해 참고 클립 요청을 등록합니다.

같은 시간에 다른 카메라에서 별도 이벤트가 생성되면 별도 사건으로 유지합니다. 구역·시간·PPE만으로 자동 병합하지 않습니다. 이 PR은 관리자 수동 병합·카메라 보정·좌표 자동 판정을 구현하지 않습니다. 수동 병합의 검토 완료 사건 허용 범위는 별도 합의가 필요합니다.

## 관리자 그룹 API

아래 API는 관리자 Bearer 인증이 필요합니다. 작업자는 접근할 수 없습니다.

| API | 내용 |
| --- | --- |
| `POST /api/camera-groups` | 그룹 생성, 201 반환 |
| `GET /api/camera-groups?limit=50&offset=0` | 목록, 최대 100개 |
| `GET /api/camera-groups/{group_id}` | 그룹·구성 카메라와 현재 PC 연결 조회 |
| `PUT /api/camera-groups/{group_id}` | 이름과 전체 구성 카메라 교체, `expected_version` 필요 |
| `DELETE /api/camera-groups/{group_id}?expected_version=0` | 그룹 삭제, 과거 이벤트·클립 요청은 유지 |

생성 본문은 다음과 같습니다. 수정 시 `expected_version`을 추가합니다.

```json
{"name": "프레스 작업 위치", "camera_ids": ["CAM_A", "CAM_B"]}
```

그룹 이름은 1~200자, 카메라는 2~100개이며 등록된 서로 다른 ID여야 합니다. 검증이 실패하면 그룹·구성 변경을 모두 취소합니다. 작성·변경 관리자는 인증 정보에서 결정하고 버전 충돌은 409로 반환합니다.

응답의 `camera_ids`는 ID 목록이며 `cameras`에는 기존 카메라 조회와 같은 위치·구역·상태·`source_node_id`·`output_node_id`가 들어 있습니다. 기존 `GET /api/cameras` 응답 구조는 바꾸지 않았습니다. 카메라 하나가 여러 겹치는 그룹에 속할 수 있지만 같은 이벤트의 동일 참고 카메라 요청은 하나만 등록합니다.

그룹 자체를 같은 사람·동일 사건이라는 증거로 사용하지 않습니다. 비활성 카메라는 설정에 남아 있을 수 있지만 새 참고 요청 대상에서 제외합니다. 서로 다른 구역이라도 촬영 구간이 겹친다면 관리자가 명시적으로 같은 그룹에 등록할 수 있습니다.

## 이벤트 생성과 참고 요청

기존 `insert_candidate_event` 저장 트랜잭션 안에서 그룹 참고 요청을 생성합니다. 이벤트 생성 이후 그룹을 바꾸거나 삭제해도 과거 요청은 수정·삭제하지 않습니다. 과거 이벤트에 신규 그룹 설정을 소급 적용하지 않습니다.

예를 들어 A와 B를 그룹으로 등록한 뒤 A 이벤트 E가 생성되면 B의 `event_clip_request`가 `pending`, `role=reference`로 생성됩니다. 이벤트 E는 기존대로 한 건이며 방송 요청도 기존 A 이벤트 생성 경로를 따릅니다. B가 독립적으로 위반을 탐지해 이벤트 F를 만들면 F는 E와 별도로 유지합니다.

요청 등록은 영상 파일 확보·처리 완료를 뜻하지 않습니다. 실제 클립 확보와 전송은 AI·시스템 통합 프로그램이 아래 계약으로 연결해야 합니다.

## 처리 node용 조회·접수 계약

```http
GET /api/processing/events/{event_id}/clip-requests
Authorization: Bearer <처리 권한이 등록된 서버 node 토큰>
```

응답은 `event_id`, 기존 이벤트의 `timestamp_start`, `timestamp_end`, `items`를 제공합니다. 각 항목에는 `request_id`, `camera_id`, `source_node_id`, `role`, `status`가 포함됩니다. 일반 현장 node·관리자 사용자 토큰으로는 처리 node API를 사용할 수 없습니다. 삭제 결정 이벤트는 409로 거절합니다.

AI·통합 담당의 연결 순서는 다음과 같습니다.

1. 기존 이벤트 생성 후 이 API로 참고 요청을 조회합니다.
2. 해당 카메라의 같은 사건 시간대 버퍼에서 클립을 확보합니다. 앞뒤 추가 길이·미래 프레임 대기·PC 시간 동기화는 #139의 클립 생성 기준과 함께 맞춥니다.
3. 기존 `POST /api/processing/events/{event_id}/clip?request_id=...`에 MP4 바이너리 본문을 전송합니다. 카메라를 생략하면 요청의 카메라를 사용하며, 명시한 카메라가 요청과 다르면 거절합니다.
4. 서버가 DB에 저장된 요청의 역할로 접수합니다. 참고 카메라는 `reference`이고 기존 원본 카메라 클립 요청은 `clip`입니다. 요청 역할을 다른 값으로 바꿔 접수할 수 없습니다.
5. 기존 GPU worker가 비식별화하고 완료된 결과만 이벤트의 미디어에 제공합니다. 참고 카메라 미디어도 같은 보관·삭제·동의·원본 비공개 정책을 적용합니다.

현재 단계에서는 전송 명령을 네트워크로 자동 발송하거나 AI 프로그램의 버퍼를 직접 소비하지 않습니다. 버퍼에 필요한 구간이 없다면 기존 관리자 클립 요청 상태 API로 실패/확보 불가를 보고해야 하며, 실패한 파일을 완료된 영상으로 표시하지 않습니다.

## DB·검증·선행 조건

스키마 v12→v13에서 그룹·구성 테이블과 클립 요청 `role`을 추가합니다. 기존 요청의 역할은 `clip`으로 보존합니다. #167 → #168 → 이 PR 순서로 반영해야 합니다. 배포 DB는 변경하지 않았습니다.

임시 DB와 가짜 클립 수신으로 관리자 권한, 구성 변경 원자성·버전, 여러 그룹의 요청 중복 방지, 비활성 카메라 제외, 별도 사건 유지, 과거 요청 유지, 처리 node 권한, 참고 역할·카메라 검증, v12 이관을 확인합니다. 실제 카메라의 두 시점 영상을 확보하는 전체 검증은 AI·현장 프로그램 연결 후 필요합니다.
