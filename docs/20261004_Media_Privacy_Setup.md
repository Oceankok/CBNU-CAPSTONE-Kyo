# 이벤트 미디어 비식별화·보관/삭제 연동

2026-10-06 재처리·검토 상태 변경은 [미디어 복구 및 검토 API 계약](20261006_Media_Recovery_Review_Contract.md)을 참고합니다. 아래 과거 모델 비교 기록과 현재 운영 계약을 구분합니다.

> 현재 적용 기준 (2026-10-06): 신규 처리는 SCRFD GPU(기본)와 YuNet GPU(`enhanced`)만 지원한다. 아래 CPU/3방식 비교 설명은 이전 개발 기록이며, 현재 절차는 마지막 절을 따른다.

이번 변경은 이벤트 DB, 서버 얼굴 처리, 관리자 검토 화면을 한 흐름으로 연결한다. 자동 카메라 그룹 클립 요청과 수동 이벤트 병합은 아직 포함하지 않는다. 여러 카메라의 자료를 동일 이벤트에 직접 첨부하는 구조를 먼저 제공한다.

## 현재 로컬 실행 준비 — SCRFD 기본값

프로젝트 루트에서 실행한다. NVIDIA GPU/CUDA PyTorch 환경에서 기존 CPU용 `onnxruntime`이 설치돼 있다면 이를 제거하고 GPU 패키지만 유지한다. `requirements.txt`에 `onnxruntime-gpu`가 포함되며 `insightface` 전체 패키지는 필요하지 않다.

```powershell
python -m pip install -r backend/requirements.txt
```

모델 가중치는 pip 설치에 포함되지 않는다. 공식 SCRFD 다운로드 링크가 작동하면 10G ONNX를 사용한다. 해당 OneDrive 링크가 인증 오류를 반환하는 경우 다음 공식 배포본에서 직접 준비할 수 있다.

1. [InsightFace v0.7 공식 배포본](https://github.com/deepinsight/insightface/releases/tag/v0.7)에서 `buffalo_l.zip`을 다운로드한다.
2. 압축파일에서 **`det_10g.onnx`만** 추출한다. 얼굴 인식/속성/정렬 파일은 사용하지 않는다. 공식 Model Zoo는 buffalo_l의 얼굴 탐지 모델을 SCRFD-10GF로 명시한다.
3. 추출 경로에 맞춰 등록한다.

```powershell
python -m backend.media.setup_scrfd --source "C:\Users\robin\Downloads\det_10g.onnx" --noncommercial-research
```

기본 등록 결과는 `models/privacy/scrfd_10g_bnkps.onnx`와 동일 이름의 `.manifest.json` / `.LICENSE.txt`다. 실제 파일명이 `det_10g.onnx`여도 등록 경로는 같으며, 등록 시 로컬 SHA-256을 기록하고 처리 시 대조한다. 모델은 Git에서 제외되고, 비상업적 연구 전용 조건을 따른다. 직접 경로를 지정하려면 등록 명령과 서버 실행 환경 양쪽에 `PPE_SCRFD_MODEL_PATH`를 동일하게 설정한다.

YuNet GPU도 선택하려면 다음 모델 준비를 추가한다.

```powershell
python -m backend.media.setup_model
```

필요한 새 테스트 DB는 기존 `init_db.py` 절차로 준비하고 백엔드/Vite를 시작한다. 모델이 없으면 웹에 SCRFD 설치 필요 안내와 실패 상태를 표시하며 결과 URL은 제공하지 않는다. 등록 정보가 없거나 체크섬이 다르면 별도의 오류를 표시한다. 대체 YuNet 사용에는 YuNet 모델도 준비돼 있어야 한다.

## 실행 전 준비 (사용자가 직접 수행)

아래 명령은 프로젝트 루트에서 현재 사용하는 시스템 Python으로 실행한다. 이 프로젝트는 가상환경을 사용하지 않는다. 기본 비식별화는 SCRFD GPU이며, Python 의존성과 모델 파일을 모두 준비해야 한다.

```powershell
python -m pip install -r backend/requirements.txt
python -m backend.media.setup_model
python backend/db/init_db.py
```

첫 명령은 의존성을 설치하거나 변경한다. 둘째는 OpenCV YuNet ONNX 모델과 라이선스를 `models/privacy/`에 다운로드하며 모델 SHA-256을 확인한다. 앱 시작 시 자동 다운로드하지 않는다. 셋째는 기본 DB를 생성하거나 기존 DB에 버전 3 마이그레이션과 누락된 seed 행을 적용한다. 기존 DB를 유지하려면 서버를 종료한 상태에서 먼저 백업한다. `PPE_DB_PATH` 환경변수로 별도 DB 경로를 지정할 수 있다.

기존 방식대로 백엔드와 Vite를 실행한 후 관리자 계정으로 로그인한다. 프론트 요청과 `/storage` 요청은 기존 동일 출처 프록시를 사용한다.

## 직접 확인할 항목

1. 검토 화면에서 테스트용 후보 이벤트를 열고 **참고 자료 추가**에 등록된 카메라 ID와 얼굴이 보이는 JPEG/PNG를 선택한다. 업로드 후 이미지가 나오고 얼굴이 모자이크되는지 확인한다. 탐지 누락 가능성이 있으므로 원본과 눈으로 비교한다.
2. 같은 이벤트에 다른 등록 카메라 ID의 짧은 MP4를 추가한다. 두 자료가 하나의 이벤트에 표시되고, 영상 전체 구간에서 얼굴 처리가 적용되는지 확인한다. 출력 영상은 음성을 제거한다.
3. 보류 상태에서는 보관/삭제 선택이 비활성인지 확인한다. 최종 검토를 완료한 뒤 동의 확인과 근거를 입력해 보관한다. 이 입력은 관리자의 동의 확인 기록이며 시스템이 실제 동의를 자동 검증하지는 않는다.
4. 테스트 자료만 사용해 **동의 없음 / 철회 · 파일 삭제**를 선택한다. 모든 연결 미디어가 삭제되고 사건 및 검토 기록은 남는지 확인한다. 이전 미디어 URL을 다시 요청하면 404가 나와야 한다. 삭제 결정은 되돌릴 수 없다.
5. 로그인하지 않은 요청과 작업자 계정으로 관리자 미디어 API에 접근할 수 없는지 확인한다. `/storage`는 기존 관리자 미디어 쿠키가 필요하며, DB에서 `ready` + `complete`인 파일만 제공한다.
6. 얼굴 모델을 준비하지 않은 상태에서는 실패 상태가 표시되고 원본이 공개되지 않는지 확인한다. 실패 후에는 모델을 준비하고 비공개 원본이 남아 있으면 재처리한다. 원본이 없거나 만료된 경우에는 자료 재수신이 필요하다.

업로드 원본은 공개 저장소 밖 `.private_media/originals/`에 기본 24시간 보관하여 재처리에 사용한다. 변환 중간 파일은 완료/실패 후 제거하며, 원본 만료 정리는 maintenance가 수행한다. 삭제 결정 시 원본과 처리 결과를 함께 삭제한다. 결과물은 `storage/candidate_events/processed/`에 저장된다. 외부 파일을 인자로 받은 이벤트 생성 서비스는 비공개 복사본을 만들고 호출자가 소유한 원본은 삭제하지 않는다.

## API

모든 아래 API는 관리자 Bearer 인증을 사용한다. 검토자 및 보관 결정자는 인증 사용자에서 결정한다.

| API | 용도 |
| --- | --- |
| `GET /api/events/{event_id}/media` | 카메라별 미디어와 보관 상태 |
| `POST /api/events/{event_id}/media?kind=image&camera_id=CAM_ID&role=reference` | 파일 자체를 요청 본문으로 업로드 (multipart 아님) |
| `POST /api/media/{media_id}/redact` | 앱 소유 기존 자료 비식별 처리 |
| `PUT /api/events/{event_id}/retention` | 최종 검토 후 보관/삭제 결정 |
| `POST /api/events/{event_id}/retention/retry` | 실패/진행 중 삭제 재시도 |

보관 요청 예시:

```json
{"decision":"retain","expected_version":0,"consent_confirmed":true,"consent_reference":"시연 자료 이용 동의 기록 001","retain_until":"2026-11-15T00:00:00+09:00"}
```

삭제 요청은 `decision: "delete"`와 조회한 최신 `expected_version`을 전달한다. 동시 수정 시 409로 거절한다. 보관 종료 시각은 선택이며 시간대를 포함해야 한다.

## 정리 프로세스

보관 만료 처리와 비정상 종료 후 임시 파일 정리는 별도 프로세스가 담당한다. 사용자가 필요할 때 실행하며 서버 시작만으로 자동 실행되지 않는다.

```powershell
python -m backend.media.maintenance --once
# 지속 실행이 필요하면 별도 터미널에서:
python -m backend.media.maintenance --interval 60
```

이 명령은 만료된 보관 파일, 삭제 대기 파일, 1시간 이상 지난 앱 소유 임시 폴더와 미등록 처리 결과물을 실제 삭제한다. 작업이 진행 중인 프로세스를 강제 종료하지 말고 서버와 정리 프로세스를 함께 관리한다. 프로세스가 중단되면 임시 원본이 다음 정리까지 남을 수 있다.

## 현재 제한

- 얼굴 탐지는 완전한 비식별화를 보장하지 않는다. 얼굴이 작거나 가려진 장면은 시연 자료로 직접 확인해야 한다. 실패한 처리의 원본 공개 fallback은 없다.
- 영상은 기본 최대 60초, 업로드는 최대 100MB이다. 각각 `PPE_MEDIA_MAX_VIDEO_SECONDS`, `PPE_MEDIA_MAX_UPLOAD_BYTES`로 조절한다.
- 영상은 모든 프레임을 처리한 뒤 H.264 MP4로 변환하며 오디오를 제거한다. 긴 영상이나 다수 동시 요청용 작업 큐는 아직 없다.
- 이벤트 생성 서비스의 미디어 처리는 동기 방식이다. 방송 명령은 미디어 처리 전에 등록하지만 호출자는 변환 완료까지 기다릴 수 있다.
- 자료 보관은 학습 후보 파일 유지까지만 수행한다. 자동 학습이나 데이터셋 내보내기는 포함하지 않는다.
- 기존 미디어는 `legacy_unverified`로 가져오며 처리 완료 전에는 제공하지 않는다. 실제 파일이 없는 더미 경로는 재업로드가 필요하다. 프로젝트 저장소 밖의 기존 절대 경로는 자동 삭제하지 않는다.

얼굴 모델 출처: [OpenCV Zoo YuNet](https://github.com/opencv/opencv_zoo/tree/main/models/face_detection_yunet).

## 레거시 / GPU 개선 방식 비교 (추가)

여기서 레거시는 최초 구현이 아니라 **직전의 CPU 회전 탐지 방식**이다. 두 방식은 같은 YuNet ONNX 가중치를 쓰며, 새 얼굴/머리 모델을 다운로드하지 않는다. GPU 추론과 영상 내부의 짧은 위치 추적을 새 처리 경로로 분리했다. Person-PPE 매칭, 개인 식별, 카메라 간 Re-ID는 추가하지 않는다.

| 항목 | `legacy` | `enhanced` |
| --- | --- | --- |
| 추론 | OpenCV CPU | ONNX Runtime CUDA |
| 영상 기본 검출 | 매 프레임 | 매 프레임 |
| 좌우 90도 회전 | 매 프레임 | 약 0.4초마다 + 위치 추적 실패 시 |
| 검출 기준 | 0.45 | 원본 방향 0.65 / 회전 방향 0.75 |
| 짧은 검출 누락 | 즉시 모자이크 누락 가능 | 확인된 추적은 움직임 유효 시 최대 약 0.8초 유지, 움직임까지 실패하면 약 0.12초 예측 후 종료 |
| 이미지 | 원본 및 좌우 회전 | 원본 및 좌우 회전, 시간적 추적 없음 |
| MP4 인코딩 | CPU `libx264`, 오디오 제거 | 동일 (이번 비교에는 NVENC 미포함) |

검출 기준을 높여 사물 오탐을 줄이는 방향이지만 작은 얼굴 검출은 감소할 수 있다. 새 방식은 모델 입력 크기에 맞게 이미지를 축소·패딩하므로 입력 해상도도 레거시와 다르다. 따라서 이 비교는 GPU만의 속도 차이가 아니라 전체 처리 방식의 품질·속도 비교이다. 회전 탐지가 모든 중간 각도를 해결하지 않으며, 추적도 장시간 가림이나 처음부터 뒷모습인 사람의 머리를 보장하지 않는다. 장면 전환으로 판단되면 이전 추적을 초기화한다.

### 사용자가 직접 준비

서버를 종료한 뒤 프로젝트 루트에서 실행한다. 이미 얼굴 모델이 준비돼 있으면 재다운로드하지 않는다.

```powershell
python -m pip install -r backend/requirements-media-gpu.txt
python backend/db/init_db.py
```

첫 명령은 추가 GPU 런타임 및 필요한 의존성을 설치한다. 둘째는 기존 DB에 처리 방식·실행 backend·처리 시간 컬럼을 추가하는 버전 3 마이그레이션을 적용한다. 이번 코딩 작업에서는 두 명령을 실행하지 않았다. 기존 결과물에는 방식과 시간이 없으므로 임의로 추정해 채우지 않는다.

조사 당시 시스템 Python에 `torch 2.11.0+cu128`은 설치돼 있고 `onnxruntime-gpu`는 없었다. 선택한 ORT 범위는 CUDA 12 / cuDNN 9 계열이며 Windows에서는 PyTorch의 관련 DLL을 먼저 불러온다. `onnxruntime` CPU 패키지를 GPU 패키지와 동시에 설치하지 않는다. CUDA provider 초기화 또는 추론이 실패하면 새 방식은 실패로 표시하고 레거시 결과로 대체하지 않는다. 서버 로그에 초기화 오류의 상세 원인을 남긴다. 호환성 참고: [ONNX Runtime CUDA 공식 문서](https://onnxruntime.ai/docs/execution-providers/CUDA-ExecutionProvider.html).

### 웹에서 직접 비교

1. 백엔드와 Vite를 재시작하고 관리자 계정으로 이벤트 검토 화면을 연다.
2. **참고 자료 추가**에서 등록된 카메라 ID와 **원본** JPEG/PNG 또는 MP4를 선택한다. 이미 모자이크된 결과물을 입력하면 비교가 유효하지 않다.
3. **같은 파일로 두 방식 비교**를 누른다. 같은 브라우저 파일을 레거시 → 새 방식 순서로 두 번 업로드하며, 기존 결과물을 덮어쓰지 않고 별도 미디어 두 건을 생성한다. 두 건 모두 해당 이벤트의 보관/삭제 정책을 따른다. 첫 요청에 통신 오류가 발생하면 중단되며, 새 방식만 실패하면 레거시 결과와 새 방식의 실패 기록이 함께 보인다.
4. 각 결과의 처리 방식, 처리 시간, backend, 프레임 수를 확인한다. GPU 방식은 `onnxruntime-cuda`로 표시된다. 처리 시간에는 모델 초기화·프레임 처리·인코딩이 포함되고 브라우저 업로드 시간은 포함되지 않는다.
5. 결과를 내려받아 같은 시각을 비교한다. 사물 오탐, 가림 시 모자이크 유지, 옆얼굴·누운 얼굴, 넘어지는 동안 각도 변화, 장면 전환 후 잘못된 영역 유지 여부를 본다.
6. 얼굴/유지 영역 누적은 매 프레임에 적용한 영역을 합산한 수치이며 서로 다른 사람 수가 아니다. 첫 실행에는 CUDA DLL 로딩과 초기화 비용이 들어갈 수 있으므로 속도 비교가 필요하면 같은 원본으로 한 번 더 수행한다. GPU 사용률이 낮더라도 작은 모델, CPU 영상 입출력·인코딩·추적이 영향을 줄 수 있다.

한 방식만 확인하려면 드롭다운에서 선택하고 **업로드 후 얼굴 처리**를 누른다. API 업로드에는 `redaction_mode=legacy` 또는 `redaction_mode=enhanced` 쿼리를 추가한다. 생략하면 기존 호환성을 위해 레거시를 사용한다. `POST /api/media/{media_id}/redact`에도 같은 쿼리를 사용할 수 있지만, 이미 `ready`인 결과의 재처리는 허용하지 않으므로 비교할 때는 원본을 다시 업로드한다.

## 추적 보완 및 속도 진단 — tracking-v2

이번 수정은 레거시 검출 조건과 YuNet 가중치를 유지한다. 추가 패키지 설치나 DB 마이그레이션은 없다. 백엔드를 재시작하고 새 결과를 만들어 비교한다. 기존 결과물은 자동으로 바뀌지 않는다.

- 기존 얼굴과의 연결에 면적 비율(0.5~2), 중심 이동 거리, IoU를 함께 사용한다.
- 확인된 얼굴의 80% 이상을 덮으면서 면적이 2.5배를 넘는 새 후보는 크기 급증 후보로 제외한다. 모든 몸통 오탐을 막는 규칙은 아니며, 실제 얼굴의 급격한 확대나 여러 사람의 겹침에서도 확인이 필요하다.
- 처음 검출된 얼굴은 즉시 모자이크하되, 두 번 연결되기 전에는 검출 누락 시 긴 유지 시간을 부여하지 않는다. 새 얼굴을 확인하려고 처음 몇 프레임을 의도적으로 노출하는 방식은 사용하지 않는다.
- 움직임 검증이 실패하면 그 위치에서 옷/배경 특징점을 새로 뽑지 않는다. 약 0.12초 동안 감쇠한 이동량으로 예측한 뒤 추적을 종료한다. 얼굴 검출만 누락되고 움직임 추적은 유효하면 최대 약 0.8초 유지한다.
- 특징점은 얼굴 영역을 잘라 추출한다. 움직임 계산에는 긴 변 최대 640픽셀의 영상을 쓰고, 여러 얼굴의 점들을 한 번에 계산한다. GPU 얼굴 검출 입력 조건은 앞 절과 같다.
- GPU 모델은 서버 프로세스당 하나를 재사용한다. 모델 파일이 바뀌면 새로 만들고, 영상별 추적 상태는 공유하지 않는다. 여러 요청의 GPU 추론은 순차 실행하며 대기 시간도 검출 시간에 포함된다.

### 직접 확인할 순서

1. 백엔드를 재시작한다. 이미 DB 버전 3과 GPU 패키지가 준비됐다면 초기화/설치 명령은 다시 실행하지 않는다.
2. 기존 297프레임 원본을 두 방식으로 비교한다. 특히 약 8.8~9.6초의 몸통 오탐과 얼굴 모자이크 누락을 확인한다.
3. 서버를 재시작하지 않고 **새 방식만 같은 원본으로 한 번 더** 실행한다. 첫 실행과 재사용 실행을 구분한다.
4. 각 처리 완료 시 백엔드 터미널에 출력되는 `media_profile {...}` 한 줄을 확인한다. `media_id`로 결과를 구분하며 `profile.revision`은 `tracking-v2`이다.
5. 정면/측면, 눕거나 넘어지는 각도 변화, 짧은 가림, 장면 전환도 확인한다. 전술 헬멧 사례는 이번 평가에서 제외한다.

`profile` 안의 주요 항목:

| 항목 | 의미 |
| --- | --- |
| `cache_reused` | GPU 모델 재사용 여부. 재시작 후 첫 GPU 요청은 false, 같은 프로세스의 후속 요청은 true |
| `model_init_seconds` | 모델 검증·생성 또는 캐시 조회 시간 |
| `detection_seconds` | 회전·크기 조절·추론·박스 후처리를 포함한 전체 검출 시간. 순수 GPU 커널 시간은 아님 |
| `tracking_seconds` | 특징점·움직임 계산과 추적 연결 시간 |
| `pixelation_seconds` | 모자이크 적용 시간 |
| `decode_seconds` | 프레임 읽기 시간 |
| `intermediate_write_seconds` | 중간 AVI 작성 시간 |
| `encoding_seconds` | 최종 MP4 변환 시간 |
| `detection_passes` | 회전을 포함한 검출 호출 수 |
| `held_regions` | 현재 프레임의 새 검출 없이 유지한 영역 누적 |
| `rejected_size_jumps` | 크기 급증 후보를 제외한 횟수 |
| `expired_tracks` | 검출/움직임 유지 조건을 벗어나 종료한 추적 수 |

상세 통계는 서버 로그에만 남으며 웹에는 기존 전체 처리 시간이 표시된다. 전체 시간에는 표 항목 이외의 파일 준비·정리 등도 일부 포함될 수 있다. 속도와 품질 개선 여부는 아직 실행 검증되지 않았다.

오탐 원인을 프레임별로 확인해야 할 때만 서버 시작 전에 같은 PowerShell에서 아래 설정을 사용한다.

```powershell
$env:PPE_MEDIA_TRACE = "1"
```

이후 기존 백엔드 실행 명령으로 시작한다. `media_trace`에는 프레임 번호(0부터), 모델 검출 박스 `detected`, 모자이크 적용 대상 `masks`, 크기 급증으로 제외한 `rejected`, 유지한 영역 수 `held`가 기록된다. 박스는 원본 좌표의 `[x, y, width, height, score]`이며 실제 모자이크에는 기존 30% 여백이 추가된다. `trace_id`를 최종 `media_profile.profile.trace_id`와 연결할 수 있다. 실제 이미지 픽셀은 로그에 남기지 않는다. 로그량이 늘어나므로 처리 속도 비교 때는 `$env:PPE_MEDIA_TRACE = "0"`으로 설정하고 서버를 재시작한다.

## SCRFD 10G 얼굴 모델 비교 (2026-10-06)

`redaction_mode=scrfd`를 추가했다. 기존 `legacy`/`enhanced`는 유지하며, 기본값도 `legacy`다. SCRFD는 CUDA 추론과 기존 영상의 짧은 가림 유지 로직을 사용한다. 이미지에서는 회전 탐지만 하고 시간 기반 유지는 하지 않는다. 새 의존성이나 DB 마이그레이션은 필요하지 않으며, 기존 GPU용 ONNX Runtime 구성이 필요하다.

### 사용 범위와 모델 준비

학습된 가중치는 비상업적 연구 전용이다. 캡스톤의 개발·비교 실험·발표 목적으로 사용하며 사업장 운영·제품 배포 용도로 사용하지 않는다. 출처와 사용 범위는 [SCRFD 안내](SCRFD_Third_Party_Notice.md)에 기록했다.

1. [공식 SCRFD Pretrained-Models](https://github.com/deepinsight/insightface/tree/master/detection/scrfd#pretrained-models)의 **SCRFD_10G** 또는 **SCRFD_10G_KPS** 링크에서 모델을 받는다. 압축파일이면 풀어서 ONNX 파일을 찾는다. `buffalo_l` 전체 패키지나 얼굴 인식 모델은 필요 없다.
2. 프로젝트 루트에서 아래 명령의 경로를 실제 ONNX 파일로 바꾸어 실행한다. 이 명령은 모델 복사·로컬 체크섬·출처 메모 등록만 수행하며 추론이나 DB 생성은 하지 않는다.

```powershell
python -m backend.media.setup_scrfd --source "C:\Users\robin\Downloads\scrfd_10g_bnkps.onnx" --noncommercial-research
```

기본 설치 위치는 `models/privacy/scrfd_10g_bnkps.onnx`다. `PPE_SCRFD_MODEL_PATH`로 변경할 수 있으며 등록 명령과 서버에서 같은 환경변수를 사용해야 한다. 기존 파일은 자동으로 덮어쓰지 않는다. 의도적으로 교체하려면 `--replace`를 추가한다. 로컬 체크섬은 처음 등록한 파일이 이후 변경됐는지 확인하는 용도이며, 다운로드 제공자의 진위를 입증하지는 않는다. 모델 자동 다운로드와 앱 시작 시 설치는 하지 않는다. 실제 ONNX 입력/출력 호환성은 최초 처리 시 확인한다.

3. 실행 중인 백엔드를 종료하고 기존 명령으로 다시 시작한다. 필요하면 프론트도 다시 시작한다.

### 사용자가 수행할 비교

1. 기존 이벤트의 **참고 자료 추가**에서 **SCRFD 비교**를 선택한다.
2. 비교 기준으로 **YuNet 개선 · GPU** 또는 **레거시 YuNet · CPU**를 선택한다.
3. 모자이크 전 원본을 선택하고 **같은 파일로 기준 방식과 SCRFD 비교**를 누른다. 두 요청은 순차 처리되며, 각각 별도 미디어 레코드가 생성된다. 첫 요청 성공 후 둘째가 실패하면 첫 결과는 남는다.
4. 빨간 안전모 작업자의 시작 구간, 오른쪽 작업자의 옆얼굴, 누운 사람과 자세 변화 구간을 같은 시각으로 비교한다. 얼굴 노출, 몸통/손 오탐, 안전모 착용 여부가 영상에서 확인 가능한지, 처리 시간을 기록한다.
5. `media_profile`의 `face_model`, `cache_reused`, 단계별 시간을 확인한다. 각 모델의 첫 실행은 초기화 시간이 포함된다.

SCRFD 기본 탐지 기준은 0.50, 회전 영상은 0.55다. YuNet과 점수 의미가 같다고 가정하지 않으며, 이 비교는 모델별 초기 설정을 포함한 처리 결과 비교다. 개선을 확인하기 전 SCRFD를 기본 처리 방식으로 전환하지 않는다.

이 변경은 얼굴 모델 비교만 추가한다. 머리 전체를 가리거나 안전모 영역을 모자이크에서 빼는 기능, PPE 판정 결과의 신규 저장은 아직 추가하지 않았다. 현재 30% 여백과 시간 기반 유지가 그대로 적용되므로 안전모 보존과 뒷모습 처리를 보장하지 않는다. 관리자 화면은 처리 완료 결과만 제공하지만, `complete`는 누락 없는 비식별화를 인증하는 상태가 아니다. 누락이 있으면 원본을 다시 업로드해 비교/보완해야 한다.

## 두 GPU 방식으로 정리 (2026-10-06)

CPU 신규 처리 경로를 제거했다. 웹과 업로드/재처리 API의 기본값은 `scrfd`, 대체 선택은 `enhanced`(YuNet GPU)다. `redaction_mode=legacy` 요청은 허용하지 않는다. 이벤트 자동 생성 시 썸네일 처리도 SCRFD 기본값을 사용하므로 서버에 SCRFD 파일과 CUDA 런타임이 필요하다. DB 변경은 없으며, 과거 CPU 결과의 처리 방식 표시는 남아 있다.

웹의 참고 자료 추가에서 SCRFD 또는 YuNet을 선택할 수 있다. 비교 버튼은 항상 같은 원본을 YuNet 다음 SCRFD 순서로 처리한다. 첫 결과가 생성된 뒤 둘째 요청이 실패하면 첫 결과는 남는다. 기존 미처리 자료를 다시 처리할 때 과거 CPU/미기록 모드는 SCRFD로 처리한다.

얼굴이 보이지 않는 뒷머리는 필수 가림 대상에서 제외한다. 실제 정면·옆얼굴이 드러나는 순간의 누락 여부와 안전모 검토 가능 여부를 기준으로 평가한다. 구현에 명시적인 뒷머리 판별/모자이크 제거를 넣은 것은 아니므로 탐지·유지 로직이 일부 뒷머리를 가릴 수 있다. 얼굴 탐지 누락을 완전히 방지한다고 보장하지 않는다.

사용자가 제공한 비교 로그: 297프레임에서 YuNet 6.74초 / SCRFD 5.46초, 577프레임에서 YuNet 9.12초 / SCRFD 9.79초. 첫 비교에는 각각 모델 초기화가 포함되어 있으므로 YuNet을 항상 빠른 방식으로 표기하지 않는다. 사용자가 얼굴 가림 품질을 확인했으며, 이번 CPU 제거/기본값/UI 정리 후 추가 테스트는 실행하지 않았다.

서버를 재시작하고 웹을 새로고침하면 선택지는 두 가지로 표시된다. 다음 수동 확인은 기본 SCRFD 선택과 GPU 두 방식 비교 버튼의 동작 확인이며, 모델 품질 비교 전체를 다시 반복할 필요는 없다. 이후 검토 완료에 따른 동의 보관/동의 없음 삭제, 파일 접근 차단 및 임시 파일 정리를 확인한다.

## 사용자 수동 검증 결과 (2026-10-06)

실제 웹 UI, Swagger 및 로컬 파일 확인으로 아래 항목을 수동 검증했다.

- 보관: 동의·근거·결정자·만료 시각·version 저장.
- 삭제: URL 차단, 실제 처리 파일 삭제, 검토/이벤트 기록 유지.
- 권한: 미인증 401, worker 403 확인(관리자 미디어 API와 처리 영상 접근).
- hold: UI 비활성화 및 API 직접 retain/delete 요청 거부.
- 실패: 손상 파일 처리 실패, URL null, 원본 공개 없음.
- maintenance: 임시/잔여 경로 cleanup, 만료 삭제, 파일 잠금으로 삭제 실패 재현 후 수동 및 maintenance 재시도, 실제 파일 삭제와 Swagger 삭제 완료 상태.

가짜 seed 경로로 반복 재시도되는 현상이 관찰되어 seed.sql/seed_events.py의 미디어 경로를 비웠다. 이 마지막 seed 변경과 CPU 제거/기본값/UI 정리 이후 별도의 새 DB 초기화·회귀 테스트는 실행하지 않았다. 제공자가 게시한 해시와 대조한 모델 진위 검증, 모델 미설치 실패 경로, 현장 PC 클립 요청·수신부터 처리까지의 자동 통합 흐름은 검증 완료로 간주하지 않는다.
